1. INTRODUCTION
1.1 Présentation
Ce projet a pour objectif la mise en place d'une chaîne d'intégration et de déploiement continus (CI/CD) complète pour deux programmes de tri à bulles écrits en C. Le projet comprend deux pipelines Jenkins collaboratifs avec déclenchement automatique et intégration GitHub via webhooks.
1.2 Objectifs du projet
* Développer deux algorithmes de tri à bulles distincts (entiers et chaînes)
* Implémenter des tests unitaires automatisés (11 tests)
* Créer deux pipelines Jenkins collaboratifs (DEV et OPS)
* Intégrer Docker pour le déploiement
* Mettre en place une synchronisation Git-Jenkins automatique via Ngrok
* Support multi-plateforme (Windows et Linux)
* Trigger automatique du pipeline OPS après succès du pipeline DEV

4. DESCRIPTION DES PROGRAMMES
4.1 Programme de tri d'entiers
Fichiers : tri_bulles.c, tri_bulles.h, main_bulles.c
Le programme implémente l'algorithme de tri à bulles classique avec optimisation. Si aucun échange n'est effectué lors d'un passage, l'algorithme s'arrête car le tableau est déjà trié.
Fonctionnalités :
* Tri d'un tableau d'entiers en ordre croissant
* Optimisation avec détection de tableau trié (flag echange)
* Affichage avant et après tri
Exemple d'exécution :
========================================
       PROGRAMME TRI À BULLES
========================================
Tableau avant tri : [ 64 34 25 12 22 11 90 ]
Tableau après tri : [ 11 12 22 25 34 64 90 ]


========================================
       TRI À BULLES TERMINÉ !
========================================


Code principal (extrait) :
void tri_bulles(int tableau[], int taille) {
    int i, j, temp;
    int echange;
    
    for (i = 0; i < taille - 1; i++) {
        echange = 0;
        
        for (j = 0; j < taille - i - 1; j++) {
            if (tableau[j] > tableau[j + 1]) {
                temp = tableau[j];
                tableau[j] = tableau[j + 1];
                tableau[j + 1] = temp;
                echange = 1;
            }
        }
        
        if (echange == 0) {
            break;  // Tableau déjà trié
        }
    }
}

6. MODE OPÉRATOIRE - PIPELINE DEV

6.2 Objectifs

      * Vérifier la compilation des deux programmes
      * Exécuter tous les tests unitaires (11 tests)
      * Valider l'exécution fonctionnelle
      * Générer un rapport de tests détaillé
      * Déclencher automatiquement le pipeline OPS si tous les tests passent

Caractéristiques principales :
      * 7 stages au total
      * Utilisation de bat pour commandes Windows
      * Utilisation de Makefile.windows pour la compilation
      * Trigger automatique du pipeline OPS en fin de succès

      2. Nom du job : tri-bulles-et-chaines-dev
      3. Type : Pipeline
      4. Cliquer sur OK

Dans la section Pipeline :
      * Definition : Pipeline script from SCM
      * SCM : Git
      * Repository URL : https://github.com/Elyesssss/Jenkins.git
      * Credentials : (si repository privé)
      * Branch Specifier : */test ⚠️ Important : branche test
      * Script Path : Jenkinsfile.dev.windows
Étape 3 : Configuration du trigger GitHub
Dans la section Build Triggers :
      * Cocher GitHub hook trigger for GITScm polling
Cette option permet au webhook GitHub de déclencher automatiquement le build.
6.5 Stages détaillés
Stage 1 : Checkout
      * Récupération du code depuis GitHub (branche test)
      * Clonage du repository dans le workspace Jenkins
Stage 2 : Vérification environnement
      * Vérification de GCC (compilateur C)
      * Vérification de Make (système de build)
      * Affichage des versions pour traçabilité
Stage 3 : Compilation
      * Nettoyage du dossier build/ existant
      * Compilation de tri_bulles.exe
      * Compilation de tri_chaines.exe
      * Vérification de la création des binaires
Stage 4 : Tests unitaires
      * Exécution de test_tri_bulles.exe (5 tests)
      * Exécution de test_tri_chaines.exe (6 tests)
      * Total : 11 tests
      * Si un test échoue, le pipeline s'arrête
Stage 5 : Exécution des programmes
      * Exécution de tri_bulles.exe (validation fonctionnelle)
      * Exécution de tri_chaines.exe (validation fonctionnelle)
      * Affichage des résultats dans les logs
Stage 6 : Rapport de tests
      * Génération de rapport_dev.txt
      * Archivage des binaires compilés
      * Empreinte digitale (fingerprint) pour traçabilité
Stage 7 : Trigger OPS Pipeline
      * Déclenchement automatique du pipeline OPS
      * Passage du numéro de build DEV comme paramètre
      * Exécution asynchrone (wait: false)
6.6 Points clés
      * Rapidité : Pas de Docker, exécution en 2-3 minutes
      * Utilisation de bat : Commandes Windows batch au lieu de shell Unix
      * Tests complets : Validation des entiers ET des chaînes
      * Rapport détaillé : Archivé pour consultation ultérieure
      * Trigger automatique : Lance OPS si SUCCESS
6.7 Cas d'usage
      * Validation rapide lors d'un commit
      * Tests automatiques sur la branche test

      * Détection précoce des régressions

      * Rollback possible vers version antérieure
      * latest pointe toujours vers la dernière version

8. CONFIGURATION NGROK ET WEBHOOKS GITHUB
8.1 Pourquoi Ngrok ?
Problème : Jenkins tourne en local (localhost:8080) et n'est pas accessible depuis Internet.
Solution : Ngrok crée un tunnel sécurisé qui expose Jenkins publiquement.
GitHub (Internet)
    ↓ webhook
Ngrok (tunnel public)
    ↓ https://abc123.ngrok.io
Jenkins (localhost:8080)


8.2 Installation et configuration de Ngrok
Étape 1 : Télécharger Ngrok
      1. Aller sur https://ngrok.com/
      2. Créer un compte gratuit
      3. Télécharger Ngrok pour Windows
      4. Extraire ngrok.exe
Étape 2 : Authentification
# Obtenir le token d'authentification sur le dashboard Ngrok
ngrok config add-authtoken VOTRE_TOKEN_ICI


Étape 3 : Démarrer le tunnel
# Exposer Jenkins (port 8080 par défaut)
ngrok http 8080


Résultat attendu :

Account                       votre.email@example.com

IMPORTANT : Notez l'URL publique https://abc123xyz.ngrok.io - vous en aurez besoin pour le webhook GitHub.

10.3 Difficultés que nous avons rencontrées et nos solutions
Problème 1 : Commandes Unix sous Windows
Difficulté : Les Jenkinsfiles utilisaient sh (shell Unix) qui n'existe pas nativement sous Windows.
Exemple d'erreur :
Cannot run program "sh": CreateProcess error=2, 
Le fichier spécifié est introuvable


Notre solution :
               * Remplacement de toutes les commandes sh par bat dans les Jenkinsfiles Windows
               * Adaptation des syntaxes (echo., || exit 0, findstr au lieu de grep)
               * Création de Jenkinsfiles séparés pour Windows et Linux
________________


Problème 2 : Make clean sous Windows
Difficulté : La commande rm -rf build du Makefile ne fonctionnait pas sous Windows.
Exemple d'erreur :
process_begin: CreateProcess(NULL, rm -rf build, ...) failed.


Notre solution :
               * Création d'un Makefile.windows avec commandes Windows
               * Utilisation de rmdir /s /q au lieu de rm -rf
               * Utilisation de if exist pour vérifier l'existence du dossier
________________


Problème 3 : Docker daemon non démarré
Difficulté : Le pipeline OPS échouait car Docker Desktop n'était pas démarré.
Exemple d'erreur :
error during connect: this error may indicate that 
the docker daemon is not running


Notre solution :
               * Démarrage systématique de Docker Desktop avant les builds
               * Ajout d'une vérification docker --version dans le stage "Vérification environnement"
               * Documentation claire des prérequis
________________


Problème 4 : URL Ngrok qui change
Difficulté : La version gratuite de Ngrok génère une nouvelle URL à chaque redémarrage, ce qui invalide le webhook GitHub.
Notre solution :
               * Documentation du processus de mise à jour du webhook
               * Note dans les prérequis sur cette limitation
               * Suggestion d'utiliser un compte Ngrok payant pour URL fixe (pour usage professionnel)
________________


Problème 5 : Séparation des fichiers main
Difficulté : Au départ, un seul fichier main.c gérait les deux types de tri, ce qui rendait le code peu modulaire.
Notre solution :
               * Refactorisation en deux programmes séparés : main_bulles.c et main_chaines.c
               * Compilation indépendante des deux programmes
               * Tests séparés pour chaque programme
________________


Problème 6 : Trigger automatique entre pipelines
Difficulté : Le pipeline OPS devait être lancé manuellement après le pipeline DEV.
Notre solution :
               * Ajout du stage "Trigger OPS Pipeline" dans le pipeline DEV
               * Utilisation de la commande build job de Jenkins
               * Passage du paramètre TRIGGERED_BY pour traçabilité
________________

Annexe E : Troubleshooting
Le pipeline DEV ne se déclenche pas automatiquement
Vérifications :
               1. Ngrok est démarré : ngrok http 8080
               2. Le webhook GitHub est configuré correctement
               3. Le trigger "GitHub hook trigger for GITScm polling" est coché dans la config Jenkins
               4. L'URL du webhook se termine par /github-webhook/
               5. Le commit a été poussé sur la branche test
________________


Le pipeline OPS ne se déclenche pas après DEV
Vérifications :
               1. Le pipeline DEV s'est terminé avec succès (status: SUCCESS)
               2. Le stage "Trigger OPS Pipeline" est présent dans le Jenkinsfile DEV
               3. Le nom du job OPS est correct : tri-bulles-et-chaines-ops
               4. L'utilisateur Jenkins a les permissions pour lancer le job OPS
________________


Erreur de compilation
Vérifications :
               1. GCC est installé : gcc --version
               2. Make est installé : make --version
               3. Les fichiers source sont présents dans src/
               4. Le Makefile approprié est utilisé (Makefile.windows sous Windows)
________________


Docker build échoue
Vérifications :
               1. Docker Desktop est démarré
               2. Espace disque suffisant
               3. Le Dockerfile est présent à la racine du projet
               4. Les fichiers source sont présents
________________


Tests échouent
Actions :
               1. Exécuter les tests localement : make test
               2. Vérifier les logs pour identifier le test en échec
               3. Déboguer le code C si nécessaire
               4. Recompiler : make clean && make all
